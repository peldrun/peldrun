## 2. Identifier Model

### 2.1 Definitions

| Identifier | Owner | Format | Purpose |
|------------|-------|--------|---------|
| `chat_id` | `project_manager` | `chat_<10 hex>` | Stable identifier for a chat session. Persisted in `session.json` and `index.json`. |
| `job_id`  | `job_manager` | `job_<12 hex>` | Identifier for a single execution run. Ephemeral; recreated for each turn. |
| `run_id`  | `run_store` (PELDRUN Core) | Generated by `RunStore` | Identifier for the durable run-state record. Currently equal to `job_id` in most paths. |
| `turn_id` | `project_manager.record_turn_usage` | `turn_<n>` or `turn_<n>_<ts>` | Identifier for a completed conversation turn, stored inside `session.json.turns[]`. |

### 2.2 Critical invariants

1. **A session may have many runs.** A session can contain any number of
   turns; each turn is produced by a distinct run. `chat_id` is stable
   across the entire lifetime of the session. `job_id` changes with every
   turn.

2. **`chat_id` and `job_id` are not interchangeable.** Current code
   sometimes uses `chat.job_id || chat.id` to derive a route target; this
   is fragile and must be replaced with explicit type-narrowed code.

3. **A single run belongs to exactly one session.** `job_id -> chat_id` is
   a function; the reverse is not.

4. **`turn_id` is not a network identifier.** It is used only for
   token-usage accounting inside `session.json.turns[]`. It is never
   exposed to the frontend as a routing target.

5. **Every active run has a terminal event.** Once a run reaches a
   terminal state (final/error/cancelled), no further events will be
   dispatched for that `job_id`. Any events received afterwards must be
   discarded.

### 2.3 API surface mapping

| Endpoint | Identifier expected | Identifier returned |
|----------|---------------------|---------------------|
| `POST /api/run` | optional `chat_id` (from client) | `job_id`, `chat_id` |
| `GET /api/run/jobs/{id}` | `job_id` OR `chat_id` (resolved) | `id` (canonical `job_id`), `chat_id` |
| `GET /api/run/jobs/{id}/stream` | `job_id` OR `chat_id` | — |
| `POST /api/run/jobs/{id}/stop` | `job_id` OR `chat_id` | `job_id`, `chat_id` |
| `POST /api/run/jobs/{id}/pause` | `job_id` OR `chat_id` | `job_id`, `chat_id` |
| `POST /api/run/jobs/{id}/resume` | `job_id` OR `chat_id` | `job_id`, `chat_id` |
| `POST /api/run/jobs/{id}/respond` | `job_id` OR `chat_id` | `job_id`, `chat_id` |
| `GET /api/chats/{id}` | `chat_id` (but `job_id` also resolves) | `chat.id`, `chat.job_id` |
| `DELETE /api/chats/{id}` | `chat_id` (but `job_id` also resolves) | report |

**Note:** `resolve_chat(identifier)` in `run_routes/utils.py` accepts both
`chat_id` and `job_id` and returns `(chat_dict_or_None, resolved_chat_id)`.
This convenience must be preserved for backward compatibility. Callers
that strictly need one or the other must narrow explicitly.

## 3. Canonical `SessionStatus`

```typescript
export type SessionStatus =
  | "pending"
  | "queued"
  | "starting"
  | "running"
  | "waiting_for_input"
  | "retrying"
  | "paused"
  | "cancelling"
  | "cancelled"
  | "completed"
  | "failed"
  | "interrupted";
```

### 3.1 Semantics

| Status | Meaning |
|--------|---------|
| `pending` | Created but not yet started. |
| `queued` | Waiting for an execution slot. |
| `starting` | Initialization in progress (model loading, tool setup). |
| `running` | Execution in progress. |
| `waiting_for_input` | Suspended for human input (HITL or delegation approval). |
| `retrying` | Transient failure being retried. |
| `paused` | Suspended by operator (Pause button). |
| `cancelling` | Cancellation requested but not yet confirmed. |
| `cancelled` | Terminated by operator or system. |
| `completed` | Finished successfully. |
| `failed` | Finished with an unrecoverable error. |
| `interrupted` | Terminated by server restart or unexpected crash. **Not a user action.** |

### 3.2 Legacy normalization

| Legacy value | Canonical | Rationale |
|--------------|-----------|-----------|
| `active` | `pending` | Historic value; no clear semantics. |
| `stopped` | `cancelled` | Same meaning; standardized. |
| `done` | `completed` | Terminal success alias. |
| `error` | `failed` | Terminal failure alias. |

**Normalization must happen server-side before the value reaches the
frontend.** The frontend must never receive `active` or `stopped`.

### 3.3 Terminal states

A session status is **terminal** when it is one of:

- `cancelled`
- `completed`
- `failed`
- `interrupted`

No further status transitions are allowed after a terminal state. Any
subsequent event for the same `job_id` must be discarded.

## 4. Canonical `RunStatus`

The `RunStatus` type in `frontend/src/lib/types.ts` already matches
`SessionStatus` except for the missing `interrupted` value.

**Required change:** add `interrupted` to `RunStatus` in
`frontend/src/lib/types.ts`.

Rationale: when the backend is restarted, any session that was `running`
at restart time must be promoted to `interrupted` so the UI can display
an accurate state without pretending the run is still alive.

## 7. Deletion Policy

### 7.1 Delete chat session

**Rule:** If any run for this session is active, the delete must be
**rejected** with HTTP 409 Conflict and a clear message.

**Sequence (when safe):**
1. Check `ACTIVE_JOB_TASKS[chat.job_id]` and all job aliases.
2. If a run is registered, reject with 409.
3. Otherwise, call `chat_storage_engine.deep_delete_chat(chat_id)`.
4. Remove from `session-store` via `removeSession(chat_id)`.
5. No SSE dispatch needed.

### 7.2 Delete project

**Rule:** If any chat under the project has an active run, reject with
409 Conflict.

**Sequence (when safe):**
1. Fetch all chats under the project.
2. Check each chat's `job_id` against `ACTIVE_JOB_TASKS`.
3. If any active run exists, reject with 409.
4. Call `project_manager.delete_project(project_id)`.
5. Remove all sessions from `session-store`.
6. Remove project from `project-store`.
7. Close any `run-stream-manager` connections scoped to the project.

### 7.3 Server restart recovery

**Rule:** On backend start, scan all `session.json` where `status` is
`running`, `starting`, `paused`, or `waiting_for_input`. For each, verify
no active task exists in `ACTIVE_JOB_TASKS`. If none exists, promote the
status to `interrupted` and persist.

## 8. Bugs discovered during Phase A audit

### Bug 1 — `control.py` has broken imports

```python
from omweb.agent_bridge import dispatch_event
```

`agent_bridge.py` does not export `dispatch_event`. The correct import is:

```python
from omweb.sse_events import dispatch_event
```

The import is inside `try/except`, so the failure is silent.
**Result: stop/pause/resume SSE events are never dispatched to clients.**
This is the root cause of the `omweb:chat-status-changed` Custom Event
workaround.

### Bug 2 — `SSEEventType` has no `PAUSED` / `RESUMED`

`control.py` uses `getattr(SSEEventType, "PAUSED", "paused")`, which
returns the string `"paused"`, not an enum member. Pydantic would reject
`SSEEvent(type="paused", ...)`.

**Fix:** Use `SSEEventType.STATUS` with `data: {"status": "paused"}`. No
new enum values needed.

### Bug 3 — `streaming.py` classifies `cancelled` as `failed`

```python
final_status = "completed" if str(ev_type).lower() in ["final", "done"] else "failed"
```

**Fix:**
```python
event_lower = str(ev_type).lower()
if event_lower in ("final", "done"):
    final_status = "completed"
elif event_lower == "cancelled":
    final_status = "cancelled"
else:
    final_status = "failed"
```

### Bug 4 — `control.py` writes `status="stopped"` to session

Must be replaced with `status="cancelled"`.

### Bug 5 — `job_manager.update_status` accepts `status="stopped"`

Same issue. All `status="stopped"` in `control.py` must be `"cancelled"`.

### Bug 6 — `use-sse-stream.ts` does not handle `cancelled` event

No case in `handleEventPayload`. When a job is stopped via the backend
(e.g. from another tab), the current tab's UI is not updated.

### Bug 7 — `use-sse-stream.ts` does not handle `status` event

The `status` event is the canonical way to update lifecycle state. The
frontend ignores it entirely. This is why `omweb:chat-status-changed`
exists — it is a workaround for this missing handler.

### Bug 8 — `use-sse-stream.ts` does not use `after_sequence` on reconnect

On error, the stream is closed and never reconnected. Combined with the
backend's full-event replay on connect, this leads to missed events.

### Bug 9 — `stream-reducer.ts` does not handle `interrupted`

The reducer treats `interrupted` as unknown. It must be in the accepted
list in the `status` case.

### Bug 10 — `chat-store.loadSessionDetail` and `loadSessions` are dead code

Verified by inspecting every consumer of `useChatStore`:
- `ChatContainer`, `ChatLanding`, `AgentSelector`, `ActiveToolsModal`,
  `Composer` use only `selectedAgentId`, `setSelectedAgentId`,
  `availableAgents`, `setAvailableAgents`, `getAgentMaxSteps`.

None calls `loadSessions`, `loadSessionDetail`, `clearAllSessions`, or
`syncSessionAgentMetadata`.

### Bug 11 — `useJobStream.ts` and `lib/sse.ts` have no consumers

Verified by full-text search across all provided files: no import of
`useJobStream` and no import of `openJobStream`. These are orphaned
paths.
