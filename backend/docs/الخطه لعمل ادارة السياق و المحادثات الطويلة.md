# تقرير معماري: إدارة السياق والمحادثات الطويلة في وكيل PELDRUN

---

## 1. الملخص التنفيذي

يعتمد مشروع PELDRUN حاليًا على نمط **Agent Loop** تقليدي يرسل كل تاريخ المحادثة (رسائل المستخدم، ردود المساعد، tool calls، tool results) إلى الـ LLM في كل خطوة. هذا الأسلوب يعمل في المهام القصيرة، لكنه ينهار مع المهام الطويلة لأسباب ثلاثة:

1. **تضخم السياق**: كل خطوة تضيف tool results وtool calls جديدة، فيتضاعف حجم الـ prompt خطيًا.
2. **خلط المسؤوليات**: `session.json` يخلط بين بيانات العرض (Conversation) وبيانات التنفيذ (Execution)، مما يجعل من الصعب تحديد ما يجب إرساله للنموذج.
3. **غياب الضغط (Compaction)**: لا توجد آلية لتلخيص التاريخ القديم، مما يهدد بتجاوز نافذة السياق مع أي مهمة طويلة.

يقدم هذا التقرير معمارية مرجعية تعالج هذه المشاكل الأربع تحديدًا: **Context Manager**، **Token Budget**، **فصل Execution State عن Conversation**، و**Summary/Compaction**، مع الحفاظ على `session.json` كما هو للواجهة الأمامية، وإضافة ملف مساعد (Sidecar) `session.context.json` يُبنى بجواره.

---

## 2. المبادئ المعمارية الأساسية

### 2.1. Persistent History ≠ LLM Context

هذا هو المبدأ الحاكم. `session.json` هو **سجل دائم** يحتوي على كل شيء. أما ما يُرسل إلى الـ LLM فهو **سياق مُنتقى** مبني من هذا السجل وفق قواعد محددة. لا يجب أن يُرسل كل شيء لمجرد أنه مخزّن.

### 2.2. الفصل بين ثلاث طبقات

| الطبقة | الملف | الغرض | من يقرأها |
| :--- | :--- | :--- | :--- |
| **Conversation** | `session.json` (جزء `turns`) | عرض المحادثة كاملة للواجهة الأمامية | الواجهة الأمامية |
| **Execution** | `events.json` | سجل التنفيذ (tool calls, observations, telemetry) | التحليل + Agent Loop |
| **Context** | `session.context.json` (جديد) | سياق مُحسّن للـ LLM، مُشتق من الاثنين | Context Manager فقط |

### 2.3. Sidecar Pattern (النمط المساعد)

بدلًا من تعديل `session.json` (وهو ما قد يكسر الواجهة الأمامية)، نبني **ملفًا مشتقًا** `session.context.json` بجواره. هذا الملف:

- **قابل للحذف وإعادة البناء** في أي وقت من `session.json` و`events.json`.
- **لا يُقرأ من الواجهة الأمامية أبدًا**.
- **يُبنى من الصفر** عند كل طلب أو بعد كل turn جديد.

هذا النمط مستخدم في أنظمة إنتاجية متعددة؛ فمثلًا، `kleos-sidecar` هو وكيل خفيف يعمل بين وكلاء الذكاء الاصطناعي والخادم الرئيسي، ويعالج جلسات الوكيل بشكل غير متزامن، ويضغط المحتوى عبر LLM محلي قبل تخزينه. كما أن ADR-011 (Session Manager Ownership) يفصل بوضوح بين إدارة دورة حياة الجلسة (SessionManager) وبين الطبقة المادية (Adapter)، مع استخدام ملف Sidecar (`acp-sessions.json`) لتخزين حالة الجلسة.

## 4. المكوّنات الأربعة بالتفصيل

### 4.1. Context Manager

Context Manager هو **العقل المدبر** الذي يقرر ما يراه النموذج. مهمته الوحيدة: تجميع قائمة `messages` من المصادر المحددة، بالترتيب الصحيح.

وفقًا لـ **Microsoft Context Contract**، فإن Context Manager هو المسؤول عن **السياسة (Policy)**، بينما الـ Orchestrator مسؤول عن **الآلية (Mechanism)**. الـ Orchestrator يطلب الرسائل، وContext Manager يقرر كيف تُلائم ضمن الحدود. مبدأ أساسي: **Compaction يجب أن يكون غير مُدمّر (Non-Destructive)**؛ أي أنه يُرجع **عرضًا مضغوطًا** دون تعديل التاريخ المخزّن.

**منطق العمل**:

```python
def build_messages(sidecar, current_user_message):
    messages = []
    # 1. System instructions (ثابتة)
    messages.append({"role": "system", "content": SYSTEM_PROMPT})
    messages.append({"role": "system", "content": PROJECT_RULES})
    
    # 2. Summary (التاريخ القديم المضغوط)
    if sidecar["summary"]["content"]:
        messages.append({
            "role": "system",
            "content": f"[ملخص السياق]\n{sidecar['summary']['content']}"
        })
    
    # 3. Recent conversation (آخر N دور)
    for msg in get_recent(sidecar["conversation"], keep=RECENT_TURNS):
        messages.append({"role": msg["role"], "content": msg["content"]})
    
    # 4. Execution State (الحالي فقط، للـ Agent Mode)
    if sidecar.get("current_execution"):
        exec_text = format_execution_state(sidecar["current_execution"])
        messages.append({"role": "system", "content": exec_text})
    
    # 5. Current user message
    messages.append({"role": "user", "content": current_user_message})
    
    # 6. Token Budget
    return budget.fit(messages)
```

### 4.2. Token Budget

Token Budget هو **آلية ضبط الميزانية**. يحدد سقفًا واضحًا ويوزّع التوكنات على الأقسام.

**التوزيع المقترح**:

| القسم | النسبة | الوصف |
| :--- | :--- | :--- |
| System | 10% | التعليمات الثابتة |
| Summary | 15% | ملخص التاريخ القديم |
| Recent Conversation | 50% | آخر N دور حرفيًا |
| Execution State | 15% | حالة التنفيذ الحالية |
| Current Message | 10% | رسالة المستخدم الحالية |

**خوارزمية الضبط**:

```python
CONTEXT_LIMIT = 8000        # حسب النموذج
RESERVED_FOR_OUTPUT = 1500  # max_tokens

def fit(messages):
    limit = CONTEXT_LIMIT - RESERVED_FOR_OUTPUT
    total = count_tokens(messages)
    if total <= limit:
        return messages
    
    # قلّص بالترتيب: exec_state ← recent ← summary
    messages = trim_section(messages, "exec_state", budget["exec_state"] * limit)
    if count_tokens(messages) <= limit:
        return messages
    
    messages = trim_section(messages, "recent", budget["recent"] * limit)
    if count_tokens(messages) <= limit:
        return messages
    
    # آخر حل: فعّل compaction
    trigger_compaction()
    return rebuild_with_summary()
```

**عتبة التفعيل**: يُفعّل الضغط عند **75-85%** من السعة، وليس عند الامتلاء الكامل. هذا يمنع الاضطرار لتلخيص سياق مطلوب أثناء المهمة.

### 4.3. فصل Execution State عن Conversation

هذا هو الفصل الأكثر أهمية. **Execution State** (tool calls, observations, artifacts) ليس جزءًا من المحادثة. هو **بيانات تنفيذية (Telemetry)** تُستخدم لأغراض التحليل والمراجعة، وليس لبناء السياق.

**القاعدة**:
- `conversation` ← يُرسل دائمًا (مضغوطًا).
- `execution` (للـ turn السابق) ← **لا يُرسل**. يُلخّص في `summary`.
- `execution` (للـ turn الحالي) ← **يُرسل فقط** إذا كان النموذج في وضع Agent ويحتاج معرفة حالة التنفيذ الراهنة.

**مثال عملي**: في جلستك، الطلب الثاني (`hello.pdf`) أرسل كل tool calls وtool results من الطلب الأول (24 رسالة، 3663 tokens). بعد التطبيق، سيُرسل:

```text
[system] You are peldrun...
[system] PROJECT RULES...
[system] [ملخص السياق السابق]
         أنشأ المستخدم آلة حاسبة بثلاثة ملفات: index.html, style.css, app.js
[user]   أنشئ ملف hello.pdf يحتوي على "Hello World"
```

بدل ~24 رسالة، 4 رسائل فقط. لا tool_calls قديمة، لا نتائج مهام سابقة.

**دعم من الأدبيات**: يُوصي RFC-609 من مشروع `soothe` بفصل **تاريخ الأهداف (loop history)** عن **تاريخ المحادثة (thread state)**، مع حقن ملخصات الأهداف بشكل منفصل عن رسائل المحادثة. هذا يسمح باستمرارية سلسة داخل نفس الجلسة ونقل المعرفة عند تبديل الجلسات، مع الحفاظ على **العزل المعماري** بين تاريخ التنفيذ وتاريخ المحادثة. كما يقترح **Nebula** فصل هوية الوكيل (persistent identity) عن بيئة التنفيذ (execution runtime)، حيث تُحقن "الروح" (soul) في عمليات تنفيذ مؤقتة (bodies) عند كل تشغيل.

### 4.4. Summary/Compaction

Compaction هو **آلية الضغط**. عندما يقترب السياق من الحد، يُلخّص التاريخ القديم ويُستبدل في العرض المضغوط.

**أنواع الضغط** (مرتبة من الأخف إلى الأثقل):

| النوع | الوصف | متى يُستخدم |
| :--- | :--- | :--- |
| **Trim Tool Outputs** | حذف مخرجات الأدوات الخام (tool results) مع الاحتفاظ بملخصها | دائمًا |
| **Structural Trimming** | إزالة البيانات الوصفية (metadata, timestamps, ids) | دائمًا |
| **Conversation Folding** | طي أدوار قديمة في ملخصات موجزة | عند 70% من الحد |
| **Summarization** | تلخيص كامل للأدوار القديمة | عند 85% من الحد |

**الضغط الهيكلي غير الفاقد (Structurally Lossless Trimming)**: يقدّم **Contextual Memory Virtualisation (CMV)** خوارزمية تقليم ثلاثية المرور تحافظ على **كل رسالة مستخدم ورد مساعد حرفيًا**، بينما تزيل الحشو الميكانيكي (مخرجات الأدوات الخام، الصور base64، البيانات الوصفية). النتائج: تقليل التوكنات بمتوسط **20%** يصل إلى **86%** في الجلسات ذات الأدوات الكثيفة، مع بقاء الجدوى الاقتصادية تحت Prompt Caching. الجلسات المختلطة (أدوات + محادثة) تحقق متوسط تقليل **39%** وتصل إلى نقطة التعادل خلال 10 أدوار.

**الطي (Context Folding)**: يقدّم **pi-fold** نهجًا مختلفًا عن Compaction التقليدي. بدلًا من تلخيص المحادثة بالكامل وإعادة بدء الجلسة من الملخص، يطوي السياق القديم في مكانه مع إمكانية "فتحه" (peek/expand) عند الحاجة. هذا يتجنب المشاكل الأربع المعروفة للـ Compaction: الفقدان غير المتوقع، تدمير البنية السببية، التكلفة والزمن، والهلوسة الناتجة عن التلخيص تحت ضغط الطول.

**تحذير مهم — فخاخ الضغط**: دراسة **"Lost in Compaction"** (مايو 2026) تكشف أن الضغط ليس بلا ثمن:
- حتى **5%** من الضغط يكلف **7 نقاط مئوية** من الاسترجاع (Recall).
- عند **50%** من الضغط، تصبح المنطقة المضغوطة "شبه ميتة" (0-7% استرجاع).
- الضغط **يضر حتى الجزء غير المضغوط** من السياق: استرجاع المنطقة المتبقية ينخفض من 68% إلى 39% مع زيادة الضغط (تأثير تخفيف الانتباه).
- **الاستراتيجية الأفضل**: `FrozenRanked` > `Frozen` > `Incremental` > `Brutal`.

**الخلاصة العملية**: لا تعتمد على الضغط كأداة أساسية. اعتمد على **التقليم الهيكلي غير الفاقد** أولًا (يُزيل الحشو دون فقدان المحتوى)، واستخدم التلخيص كحل أخير عند الضرورة القصوى.

## 5. استراتيجيات توفير التوكن

إلى جانب المكونات الأربعة، هناك استراتيجيات إضافية مثبتة في أدبيات 2026:

| الاستراتيجية | الوصف | التأثير الموثّق |
| :--- | :--- | :--- |
| **Context Stratification** | فصل السياق الثابت (يُحمّل دائمًا) عن الديناميكي (يُحمّل عند الطلب) | 60-70% تقليل توكنات في بيئة إنتاجية |
| **Schema-Contracted Prompts** | تنسيق الأوامر وفق مخطط صارم يمنع الحشو | تقليل التوكنات وتحسين الاتساق |
| **Semantic Caching** | تخزين النتائج الدلالية وإعادة استخدامها | تقليل تكرار الاستدعاءات |
| **Trajectory Reduction** | تقليم مسار الأدوات وإزالة الخطوات غير الضرورية | 15.54% تقليل تكلفة في Smart Cascade |
| **Prompt Caching** | وضع التعليمات الثابتة في بداية السياق لاستفادة من التخزين المؤقت | تحسين التكلفة وزمن الوصول |
| **Progressive Disclosure** | عدم إرسال كل تعريفات الأدوات في كل مرة، بل عند الحاجة | يحافظ على نسبة الإشارة إلى الضوضاء |

**تحسين مهم**: **Deep Agents v0.7** من LangChain قلّص التوكنات الأساسية بنسبة **65%** (من ~6k إلى ~2k) عبر ثلاث تغييرات: إزالة system prompt الأساسي، تقليم أوصاف الأدوات بنسبة 43%، وجعل قوائم المهام اختيارية. التقييمات أظهرت أن الأداء لم ينخفض.
